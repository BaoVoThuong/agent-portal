# DRAFT proposal — fix table-column config hardcoding (pre-debate)

This is a first-pass proposal based on the audit in `2026-08-07-column-config-hardcoding-audit.md`. It is NOT the final plan — two reviewer agents will critique this for architecture/DRY, risk/regression-safety, and performance before a final bite-sized implementation plan gets written.

## Root cause (shared by C1, C3, C4, E1, E2, E6)

`NewTaskDialog`, `TaskDetailDrawer`, `KanbanBoard`/`TaskCard` (CS) and `NewEnrollmentDialog`, `EnrollmentDrawer`, `EnrollmentToolbar` (Enrollment) only ever receive **bare `Set<string>` of column keys** (`configuredColumnKeys`/`visibleColumnKeys`/`requiredColumnKeys`) for SYSTEM columns, never the actual `TableColumn` row (which carries `.label`, `.position`). The parent components (`TaskBoardClient.tsx`, `EnrollmentClient.tsx`) already have the full `TableColumn[]` in memory (`taskLayoutColumns` / the equivalent in Enrollment) — it's just not threaded down far enough.

## Proposed shared mechanism

1. Add one small helper, e.g. `columnLabel(columnByKey: ReadonlyMap<string, Pick<TableColumn,"label">>, key: string, fallback: string): string` — returns the live label if the key exists in config, else the fallback (so a component still renders something sane before config loads, or for a key that was never seeded). Location: `src/lib/table-config/columns.ts` (already the home of `isAutoGeneratedColumn`/`canEditColumnField`, i.e. the "column config helper" module both CS and Enrollment already import from).
2. Each parent (`TaskBoardClient.tsx`, `EnrollmentClient.tsx`) builds ONE `columnByKey: Map<string, TableColumn>` from its already-fetched `taskLayoutColumns`/equivalent (a single `useMemo`, not rebuilt per child render), and passes it down as a new prop to every consumer that currently only gets the bare key-Sets.
3. Every hardcoded label call site (C1, C2, C4-badges, E1, E2, E3, E4) changes from a literal string to `columnLabel(columnByKey, "priority", "Priority")` (fallback = today's hardcoded string, so behavior is unchanged until an admin actually renames something — zero visual diff on first deploy).

## Proposed phased scope

**Phase 1 — trivial, do first:** E3 (List-row `pcp2026`/`due` cells). Copy the exact pattern already used 2 lines away in the same function. No new plumbing.

**Phase 2 — core fix, highest value:** C1 (CS Create+Detail labels) and E1+E2 (Enrollment Detail+Create labels). Introduce the shared `columnByKey` mechanism from `TaskBoardClient.tsx`/`EnrollmentClient.tsx` down into these 4 components. This is the fix that actually makes "rename a system column in Config" work anywhere it currently doesn't.

**Phase 3 — reuse the same mechanism:** C2 (CS filter toolbar) and E4 (Enrollment filter toolbar). Same `columnByKey`, already-in-scope `listColumns`/`columns` prop just needs a lookup added.

**Phase 4 — needs new prop wiring end-to-end:** C4 (CS Kanban). Thread `configuredColumnKeys`/`visibleColumnKeys`/`columnByKey` from `TaskBoardClient.tsx` → `KanbanBoard.tsx` → `TaskCard.tsx`, gate the Priority/Category/QC badges on `visibleColumnKeys.has(...)` the same way `NewTaskDialog`/`TaskDetailDrawer` already do. OPEN QUESTION for debate: should Kanban cards ALSO gain custom-column rendering (currently renders none at all), or is that a separate feature request out of scope for a hardcoding fix?

**Phase 5 — higher risk, deferred pending debate verdict:** C3 + E6 (field ORDER in Create/Detail asides following `table_column.position`). Today's fixed JSX sequence would need to become a data-driven map over a position-sorted list of field descriptors (something like `{ key, label, required, render: () => ReactNode }[]`) for both CS and Enrollment's aside panels — a real structural rewrite of 4 large components, not a lookup swap. OPEN QUESTION for debate: is this worth doing in the same plan as the label fixes, or should it ship separately after the lower-risk phases are verified in production?

## Explicitly out of scope (per the audit's own low-confidence call)

E7 (export/sort key↔field switch statements) — same class as the already-accepted `NewTaskPayload`/route-level DB-field hardcoding, not a config-hardcoding bug.

## Questions for the debate agents

1. Is the shared `columnByKey` Map + `columnLabel()` helper the right shape, or is there a simpler/more idiomatic way given this codebase's existing patterns (e.g. should it be a hook, a context, or literally just a prop-drilled Map like `optionLabelById` already is elsewhere)?
2. Phase 4 (Kanban): fix visibility-gating only, or also add custom-column rendering? What's the actual regression risk of leaving Kanban as-is a bit longer vs. the value of fixing it now?
3. Phase 5 (order): worth doing at all in this pass? What's the concrete blast radius/regression risk of restructuring 4 large, heavily-tested-by-hand components (NewTaskDialog, TaskDetailDrawer, NewEnrollmentDialog, EnrollmentDrawer) into a data-driven render loop, given they were extensively hand-edited earlier this same session for Required-field/Stage-field work?
4. Any sequencing/dependency issues between phases, or ways to parallelize the implementation work safely (e.g. via subagent-driven-development, one task per phase)?
5. Performance: does building `columnByKey` as a `useMemo` in each parent avoid any real re-render cost, or is this a non-issue at this data scale (dozens of columns, not thousands) and not worth optimizing for?
