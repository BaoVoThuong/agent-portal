# Lead RBAC — Ai thấy gì, ai sửa gì

> **Cho người thực thi:** dùng `superpowers:subagent-driven-development` hoặc
> `superpowers:executing-plans`. Các bước dùng checkbox (`- [ ]`) để theo dõi.

**Mục tiêu:** chốt và thực thi mô hình phân quyền cho module Lead — một ma trận
duy nhất trả lời "ai thấy gì, ai sửa gì", và bịt các lỗ hổng giữa ma trận đó với
code đang chạy.

**Kiến trúc:** quyền được quyết bởi **hai lớp độc lập**:
1. **Permission (RBAC)** — `lead.manage` / `lead.work` / `lead.export`, cấp cho
   *role*, quyết định **vào được module hay không** và **có phải manager không**.
2. **Membership (agent_members)** — cặp agent ↔ assistant, quyết định **lead nào**
   một worker chạm được. Cùng bảng Task đang dùng, không có bảng thứ hai.

Mọi quyết định thuần tuý nằm trong `src/lib/leads/access.ts` (không I/O, test
được đầy đủ). Việc tra membership nằm trong `src/lib/leads/membership.ts`. Route
API là nơi *thi hành*; client gọi **cùng một kết quả đã giải sẵn** để vẽ đúng
những nút mà API sẽ chấp nhận.

**Tech stack:** Next.js 16 App Router, Supabase PostgREST + service-role,
vitest (`environment: "node"`, chỉ chạy `src/**/*.test.ts` — **không test được
`.tsx`**).

## Global Constraints

- Không tạo bảng agent/assistant thứ hai. Đọc `agent_members` qua
  `fetchAssistantAgentsForCs` / `isAgentOwnerOrAssistant` trong
  `src/lib/tasks/membership.ts`.
- Mọi thay đổi logic ghi vào `agent-portal/changelog.md`.
- Không tự push. Chạy `npm run typecheck && npm run lint && npm run test:run`
  trước mỗi commit.
- Quyết định phân quyền **chỉ** viết trong `src/lib/leads/access.ts`. Route không
  được tự chế điều kiện `if (actor.isManager || ...)` riêng.
- Fail-closed: tra membership hỏng thì **throw**, không trả mảng rỗng.

## Phần 1 — Ma trận RBAC (đây là câu trả lời)

### 1.1 Năm loại người

| # | Vai | Xác định bằng | `isManager` | `isWorker` |
|---|-----|---------------|-------------|------------|
| A | **Admin** | `portal_account.role = 'admin'`, hoặc role RBAC `Admin` / `Super Admin` | ✅ | ✅ |
| B | **Lead Manager** | có permission `lead.manage` | ✅ | ✅ |
| C | **Agent** | có `lead.work` | ❌ | ✅ |
| D | **Assistant** | có `lead.work` **và** có dòng `agent_members(agent_email = X, cs_email = mình, is_assistant = true)` | ❌ | ✅ |
| E | **Ngoài cuộc** | không có quyền lead nào | ❌ | ❌ |

D là C cộng thêm phạm vi. Một người vừa là agent của lead mình, vừa là assistant
của agent khác — hai vai cộng dồn, không loại trừ.

Code hiện tại (`src/lib/leads/access.ts`):

```ts
export function buildLeadActor(
  permissions: readonly string[] | undefined,
  email: string,
  opts?: { isAdmin?: boolean }
): LeadActor {
  const isManager =
    can(permissions, PERMISSIONS.LEAD_MANAGE) || Boolean(opts?.isAdmin);
  return {
    email,
    isManager,
    isWorker: isManager || can(permissions, PERMISSIONS.LEAD_WORK),
  };
}
```

### 1.2 Thấy gì

| Loại lead | A/B Manager | C Agent | D Assistant | E |
|---|---|---|---|---|
| Lead gán cho chính mình | ✅ | ✅ | ✅ | ❌ |
| Lead gán cho agent mình phụ tá | ✅ | — | ✅ | ❌ |
| Lead gán cho agent **khác** | ✅ | ❌ | ❌ | ❌ |
| Lead **chưa gán** (pool) | ✅ | ❌ | ❌ | ❌ |
| Overview (số liệu toàn đội) | ✅ | ❌ | ❌ | ❌ |

Phạm vi này được giải **một lần mỗi request** rồi áp vào truy vấn, không lọc ở
client:

```ts
// src/lib/leads/membership.ts
export async function resolveLeadOwnerEmails(
  actor: LeadActor
): Promise<string[] | null> {
  if (actor.isManager) return null;          // null = không lọc
  const own = actor.email.trim().toLowerCase();
  const assisted = await fetchAssistantAgentsForCs(actor.email);
  return [...new Set([own, ...assisted.map((e) => e.trim().toLowerCase())])];
}
```

```ts
// src/lib/leads/queries.ts
if (filter.ownerEmails) query = query.in("assigned_to_email", filter.ownerEmails);
```

`null` = manager (không lọc). Mảng **rỗng** sẽ có nghĩa "không dòng nào", nên hai
thứ không thể dùng chung một biểu diễn — đó là lý do kiểu là `string[] | null`
chứ không phải `string[]`.

**Ba chỗ cố ý KHÔNG cho sửa, dù là admin:**

1. `contact_attempt_count`, `first_contacted_at`, `last_contacted_at`,
   `next_follow_up_at` — bốn cột này **chỉ** `log_lead_interaction_atomic` được
   ghi. Sửa tay là phá chính con số mà engine cảnh báo đọc. `buildLeadPatch`
   từ chối chúng:

   ```ts
   // src/lib/leads/patch.ts
   export const EDITABLE_LEAD_FIELDS = [
     "full_name", "phone", "email", "product", "status_id", "next_follow_up_at",
   ] as const;
   // ...
   if (!(EDITABLE_LEAD_FIELDS as readonly string[]).includes(key)) {
     return { ok: false, error: `${key} cannot be edited here.` };
   }
   ```
   (`next_follow_up_at` có trong danh sách vì đặt lịch hẹn là việc của con
   người; ba cột đếm còn lại thì không.)

2. `assigned_to_email` — không sửa qua PATCH, phải đi `/api/leads/assign` để còn
   ghi `lead_assignment_history`.

3. Status `scheduled` mà chưa có ngày follow-up → từ chối, kèm lời nhắc mở lead
   ra ghi. Đây đúng ràng buộc `LEAD_FOLLOW_UP_REQUIRED` trong RPC.

**⚠️ ô đánh dấu ở dòng "Ghi tương tác":** hiện `canLogInteraction` **không** cho
manager ghi lên lead không phải của mình:

```ts
export function canLogInteraction(actor, lead, flags = {}): boolean {
  if (!actor.isWorker) return false;
  return isLeadOwner(actor, lead) || Boolean(flags.isOwnerOrAssistant);
}
```

Không có `if (actor.isManager) return true`. Cố ý: bộ đếm liên hệ thuộc về agent
được gán, manager ghi hộ sẽ làm agent đó trông như đã gọi. **Giữ nguyên; xem
QĐ4 ở Phần 3 — đây là điểm duy nhất chưa được chốt dứt khoát.**

## Phần 2 — Hiện trạng so với ma trận

Đã kiểm trên Supabase production ngày 2026-09-01.

### G1 — Không ai ngoài 3 admin dùng được module Lead ⛔ CHẶN

```
role_permissions where permission_key like 'lead.%'
  → lead.manage  : Admin
  → lead.work    : Admin
  → lead.export  : Admin
```

Chỉ **role `Admin`** giữ quyền lead. Bảy role còn lại — `Agent`, `Health Agent`,
`P&C Agent`, `Task CS`, `Accounting`, `Admin Health Task`, `Sub Admin` —
**không có quyền nào**, tức không ai trong số họ vào được `/leads`.

Hệ quả dây chuyền: `fetchLeadAssignees()` lấy người từ chính bảng grant đó —

```ts
// src/lib/leads/assignees.ts
.from("role_permissions")
.select("role_id")
.in("permission_key", [PERMISSIONS.LEAD_WORK, PERMISSIONS.LEAD_MANAGE]);
```

nên **dropdown "gán cho ai" hiện chỉ có 3 người**. Toàn bộ tính năng phân bổ
lead — lý do module này tồn tại — chưa chạy được với ai.

Trong khi đó `agent_members` đã có sẵn **11 cặp assistant trên 7 agent**
(`khang.nguyen@` 3 người, `ann.strambler@` 3, `linh.le@` 2, `thuy.insagent@` 1,
`jennifer.le.insagent@` 1, `bao.vo@` 1). Cấu trúc đội đã có, chỉ thiếu grant.

### G2 — `lead.export` là quyền chết

`grep -rn "LEAD_EXPORT" src` chỉ ra hai chỗ: khai báo hằng số và test hằng số.
**Không route nào, không nút nào đọc nó.** Module Lead không có tính năng export.
Quyền này đang được cấp cho Admin và không có tác dụng gì.

### G3 — Admin không thể được gán lead ⛔ DEFECT

`buildLeadActor` giờ nhận `isAdmin`, nhưng route assign kiểm tra người nhận mà
**không** truyền cờ đó:

```ts
// src/app/api/leads/assign/route.ts:25
const targetActor = buildLeadActor(targetAccess.permissions, parsed.toEmail);
if (!targetAccess.isActive || !targetActor.isWorker) {
  return NextResponse.json({ error: "That person cannot be assigned leads." }, { status: 400 });
}
```

Một account-role admin **không** được cấp `lead.work`/`lead.manage` giờ quản lý
được lead (vì `isAdmin` làm họ thành manager ở mọi chỗ khác) nhưng **không nhận
được lead**. Đây là lỗi tao tạo ra khi thêm `isAdmin`, chưa sửa.

### G4 — Không có resolver năng lực gộp

Task có `resolveTaskCapabilities(actor, task, flags)` trả về một object
`{ canView, canEditContent, canChangeStatus, canAssign, ... }` mà **cả route lẫn
client cùng gọi**, nên hai lớp không thể lệch nhau. Lead thì mỗi route tự gọi
từng hàm rời, và client tự chế lại luật:

```ts
// src/app/(authed)/leads/_components/LeadTable.tsx
function canEditLead(lead: LeadRow, editableOwnerEmails: string[] | null): boolean {
  if (editableOwnerEmails === null) return true;
  const owner = lead.assigned_to_email?.trim().toLowerCase() ?? "";
  return owner !== "" && editableOwnerEmails.includes(owner);
}
```

Hàm này *hiện* khớp server, nhưng nó là bản chép tay thứ hai của cùng một luật.
Module này đã dính trôi lệch vì copy helper ít nhất ba lần (scope table config,
find-or-create event, truy vấn từ vựng).

### G5 — Pool vô hình và không có đường tự nhận

Agent không thấy lead chưa gán, cũng không có nút nhận. Mọi phân bổ phải qua
manager. **Đây có thể là đúng ý** — xem Quyết định 3.

### G6 — Không có gì cho agent tự xem số của mình

`/api/leads/overview` là `canManageLeads`. Một agent không có chỗ nào xem "tôi
còn bao nhiêu lead chưa gọi". Nhưng cảnh báo (`?alert=`) thì họ dùng được, và
đã bị lọc theo scope.

### Những chỗ đang ĐÚNG, đừng đụng vào

- **Realtime không rò dữ liệu.** `broadcastLeadsChanged` chỉ phát `{ sourceId }`,
  không kèm dòng lead nào; client nhận tín hiệu rồi tự gọi lại `/api/leads` —
  route đã lọc theo scope. Không có đường vòng.
- **Người nhận lead được kiểm tra.** Route assign từ chối account không active
  hoặc không phải worker (trừ lỗi G3 ở trên).
- **Danh sách agent chỉ nạp cho manager.** `actor.isManager ? fetchLeadAssignees() : []`.
- **Fail-closed khi tra membership.** `fetchAssistantAgentsForCs` cố tình throw
  khi query hỏng — Task đã học bài này: nuốt lỗi ở đó từng biến một assistant
  thành người thấy toàn bộ task công ty.
- **Cờ membership chỉ nới ra.** Người không có quyền lead nào thì cờ bật vẫn bị
  chặn, đã có test trong `access.test.ts`.

## Task 1: Cấp `lead.work` cho mọi role không phải Admin

Theo QĐ1: chỉ `Admin` giữ `lead.manage`; tất cả role còn lại nhận `lead.work`.

**Files:**
- Create: `supabase/rollouts/2026-09-01-lead-role-grants.sql`

- [ ] **Bước 1: Chụp lại hiện trạng trước khi đổi**

```sql
select r.name, coalesce(string_agg(rp.permission_key, ', ' order by rp.permission_key), '(không có)') as lead_perms
from roles r
left join role_permissions rp on rp.role_id = r.id and rp.permission_key like 'lead.%'
group by r.name
order by r.name;
```

Chép kết quả vào changelog để còn quay lại được.

- [ ] **Bước 2: Kiểm tài khoản assistant thuộc role nào**

Assistant cần **cả hai**: `lead.work` (để qua cổng `requireAnyPermission` ở
`/leads`) **và** dòng trong `agent_members`. Có membership mà không có permission
thì vẫn bị chặn ở cửa.

```sql
select am.agent_email, am.cs_email, coalesce(r.name, '(không có role)') as assistant_role
from agent_members am
left join portal_account pa on lower(pa.email) = lower(am.cs_email)
left join user_roles ur on ur.user_id = pa.id
left join roles r on r.id = ur.role_id
where am.is_assistant = true
order by am.agent_email;
```

Sau bước 3 mọi role đều có `lead.work`, nên chỉ dòng `(không có role)` là vấn đề
— tài khoản đó phải được gán một role trước, nếu không họ vào không được.

```ts
// src/lib/leads/assign-target.ts
import { buildLeadActor, isLeadViewAdmin } from "./access";

export type AssignTarget = {
  isActive: boolean;
  permissions: readonly string[];
  role?: string | null;
  roles?: readonly string[];
};

/**
 * Ai được nhận một lead. Phải đọc cờ admin giống hệt buildLeadActor ở mọi chỗ
 * khác: nếu không, một account-role admin quản lý được lead nhưng lại không
 * được gán lead nào — đúng lỗi đã xảy ra khi thêm isAdmin.

export function canBeAssignedLead(target: AssignTarget): boolean {
  if (!target.isActive) return false;
  const actor = buildLeadActor(target.permissions, "", {
    isAdmin: isLeadViewAdmin(target),
  });
  return actor.isWorker;
}
```

```ts
// src/lib/leads/capabilities.ts
import {
  canEditLead, canLogInteraction, canManageLeads, canViewLead,
  type LeadActor, type LeadMembershipFlags,
} from "./access";
import type { LeadRow } from "./types";

export type LeadCapabilities = {
  canView: boolean;
  canEdit: boolean;
  canLog: boolean;
  canAssign: boolean;
};

/**
 * Một nguồn sự thật: route và client cùng gọi hàm này với cùng bộ cờ đã giải,
 * nên hai lớp không thể lệch nhau. Task đã làm y hệt với
 * resolveTaskCapabilities; Lead trước đó để client tự chép lại luật.
 */
export function resolveLeadCapabilities(
  actor: LeadActor,
  lead: Pick<LeadRow, "assigned_to_email">,
  flags: LeadMembershipFlags = {}
): LeadCapabilities {
  return {
    canView: canViewLead(actor, lead, flags),
    canEdit: canEditLead(actor, lead, flags),
    canLog: canLogInteraction(actor, lead, flags),
    canAssign: canManageLeads(actor),
  };
}
```
